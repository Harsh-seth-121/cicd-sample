Section 1 — Problem Framing

What Teams Actually Need

Confidence

Every commit reaching production has been built, tested, versioned, and verified through identical stages — no shortcuts, no drift.

Visibility

See exactly where every pipeline is, what failed, and why — without digging through runner logs or parsing webhook payloads.

Control

Pause, resume, cancel, or rerun any pipeline stage without rebuilding from scratch or SSHing into a runner.

Most CI/CD systems solve for the happy path. Production needs the unhappy path handled just as well.

Where Pipelines Break in Production

Duplicate SCM events — Trigger duplicate workflows, duplicate publishes, and repeated deployments to the same environment
Flaky build/test runners — Cause cascading retries across long-running work, amplifying cost and latency
Partial publishes — Leave orphaned image tags without manifests, or manifests without final digests
DEV failures propagating to QA — Broken builds reach higher environments when gates are weak or bypassed
Version drift between build and deploy — Pipelines that rebuild introduce non-determinism between what was tested and what was deployed
Workflow code changes — Non-determinism in orchestration path breaks in-flight pipelines during worker rollout

Design Assumptions & Constraints

We Assume

  • Source control is the single source of truth (push, PR, merge, tag)
  • Build and test must complete before versioning
  • Every branch deploys to DEV; only main progresses to QA
  • Container registry is the artifact boundary
  • Operators need real-time intervention capability
  • External systems (runners, registries, deploy tools) perform execution work

We Constrain

  • Publish once, deploy the same image digest forward — no rebuild drift
  • GitVersion runs only after required gates pass
  • Failures are contained — a DEV failure never reaches QA
  • Idempotent activities for safe retries
  • Task queues isolate failure domains
  • Deterministic workflow code — all I/O lives in activities

Success Looks Like

  • Zero duplicate deployments from duplicate webhook events
  • Sub-15-minute pipeline from push to DEV deployment
  • Any failure diagnosable within 60 seconds via dashboard or Temporal UI
  • Operators can pause, resume, cancel without SSH access or runner credentials
  • Workflow code can be updated without breaking in-flight pipelines
  • Full audit trail via Temporal event history and 9 custom search attributes
  • One command to run locally — docker-compose up --build

Containment boundaries: Temporal Cloud holds durable state. Task Queues isolate each failure domain. Publish is the boundary after which deployments consume a fixed digest. Why Temporal — And What We Traded

What We Get

  • Durable execution — workflows survive worker restarts and infrastructure failures
  • Built-in retry policies with exponential backoff and heartbeats
  • Signal / Query / Update for operator control without custom state management
  • Event history for complete audit trail of every decision
  • Search attributes for operational visibility at scale
  • Child workflows for stage isolation and independent retry scopes
  • Versioning for safe workflow code changes
  • Service accounts with API keys for clean automation boundaries

What We Accept

  • Temporal Cloud dependency — managed service as control plane
  • Determinism constraints — no I/O in workflow code, all side effects in activities
  • Learning curve for .NET SDK patterns and replay semantics
  • Additional infrastructure — 5 worker fleets to operate
  • Operational complexity — more moving parts than a monolithic CI/CD
What we intentionally did not choose: monolithic pipeline runner (Jenkins), event-driven choreography (no central state), custom queue + state machine (rebuild Temporal poorly).

Production Readiness

Failure handling, versioning, and observability

Failure Amplification Map

Failure SourceHow It AmplifiesControlRecovery
Duplicate SCM events Duplicate workflows, publishes, deployments Idempotency keys + workflow ID deduplication Resume existing execution
Flaky build/test runners Repeated long-running work, false failures Separate task queues, bounded retries, short timeouts Rerun failed stage only
Bad repo checkout Wrong version, wrong tags, publish confusion Full history checkout, explicit branch/ref context Fail before publish, fix config
Partial publish Tag without manifest, or manifest without digest Publish + manifest tracked separately, idempotent writes Replay publish/manifest stage safely
DEV deploy failure Broken build reaches higher environments QA blocked unless DEV succeeds Hold in DEV-failed state, rerun after fix
QA deploy failure Unstable release candidate partially progressed No downstream continuation after QA fail Keep artifact + evidence, retry or promote successor
Workflow code change Non-determinism in orchestration path Replay tests before worker rollout Verify with history replay before shifting traffic

Safe Workflow Code Changes

Determinism Guarantee

All workflow code is deterministic. Side effects (network calls, file I/O, timers) live exclusively in activities. Temporal replays workflow decisions from event history.

Replay Testing

Before rolling out new worker code, replay existing workflow histories against the new code to verify compatibility. Catches non-determinism before it reaches production.

Digest-Based Deploys

Published image digests are immutable. The same digest that passed DEV verification is deployed to QA. No rebuild drift. No "works on my machine."

Worker Rollout Strategy

1. Deploy new worker code alongside existing workers
2. Run replay tests against production workflow histories
3. Shift traffic to new workers via Temporal versioning
4. Drain old workers after in-flight workflows complete

Success Criteria

How we measure success, when we step back

How We Measure Success

Reliability

  • Zero duplicate deployments from duplicate webhook events
  • Zero partial publishes — every publish produces a manifest with a digest
  • Failed pipelines diagnosable within 60 seconds via dashboard or Temporal UI
  • No DEV failure ever propagates to QA

Speed

  • Push to DEV deploy under 15 minutes for standard builds
  • Push to QA under 20 minutes for main
  • Operator pause/resume round-trip under 5 seconds
  • Dashboard reflects stage changes within 3 seconds

Visibility

  • 100% of pipelines searchable by repository, branch, status, and commit
  • Dashboard shows real-time stage progression with failure details
  • Every workflow decision recorded in Temporal event history
  • Search attribute queries enable alerting and reporting

Operator Confidence

  • Any pipeline can be paused/resumed/cancelled without SSH
  • Failure evidence preserved in workflow history and search attributes
  • Redeploy from hold state without rebuilding
  • New team members productive with controls within 30 minutes

When the System Runs Itself

Maturity indicators for hands-off operation

Teams trigger pipelines and walk away — no babysitting, no refreshing logs
Failures self-classify — transient retries recover automatically, deterministic failures report immediately
Operators intervene < 5% of the time — on-call for pipelines is rare, not routine
New repositories onboard in minutes — config-driven, no code changes required
Workflow code changes deploy safely — replay testing catches issues before production
The goal is not to build the most sophisticated pipeline system. It is to build one that teams trust enough to stop thinking about.
